الوكيل (Agent) في جوهره بسيط: نموذج لغوي داخل حلقة، يملك أدوات يستدعيها، ويقرّر في كل دورة ما التالي. النمط الذي عمّم هذه الفكرة هو ReAct [1]: مزاوجة التفكير (Reasoning) بالفعل (Acting) — يفكّر خطوة، ينفّذ أداة، يقرأ النتيجة، ثم يعيد التقدير.

البساطة خادعة. الفرق بين عرض تجريبي مبهر ونظام إنتاجي ليس في النموذج، بل في الحدود والحواجز التي تحيط بالحلقة.

## الحلقة

1. **النموذج يقرّر**: يقرأ الحالة ويختار الخطوة التالية.
2. **استدعاء أداة**: ينفّذ تطبيقك الأداة بوسائطها.
3. **نتيجة الأداة** تعود إلى السياق، فيعيد النموذج التقدير — ثم تعود الدورة إلى ١.
4. **الخروج** بأحد ثلاثة: جواب نهائي، أو بلوغ حدّ التكرار، أو خطأ غير قابل للتعافي.

الحلقة تنتهي بأحد ثلاثة: جواب نهائي، أو بلوغ حدّ التكرار، أو خطأ غير قابل للتعافي. غياب الاحتمالين الأخيرين هو ما يجعل وكيلًا يستهلك خمسين استدعاءً في سؤال بسيط.

## تصميم الأداة: هنا تُربح المعركة

النموذج لا يرى الكود، يرى الوصف فقط. الوصف الرديء ينتج استدعاءً رديئًا مهما كان النموذج قويًّا.

```json
{
  "name": "search_orders",
  "description": "يبحث في طلبات العميل بحسب رقم الطلب أو بريده. يعيد حتى ٢٠ طلبًا مرتّبة من الأحدث. لا يعيد بيانات الدفع. استخدمه قبل أي إجراء على طلب للتحقق من وجوده.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "بصيغة ORD-XXXXX" },
      "email": { "type": "string", "format": "email" },
      "status": { "type": "string", "enum": ["pending", "shipped", "cancelled"] }
    },
    "oneOf": [{ "required": ["order_id"] }, { "required": ["email"] }]
  }
}
```

قواعد عملية تصمد:

- **صف متى تُستخدم الأداة ومتى لا تُستخدم**، لا وظيفتها فقط.
- **قيّد المدخلات بمخطط صارم**: `enum` بدل نصّ حرّ يمنع نصف الأخطاء قبل وقوعها.
- **أعِد أخطاءً وصفية**: `"لا يوجد طلب بهذا الرقم — تحقّق من الصيغة ORD-XXXXX"` أفضل من `"error 404"`، لأن الوكيل يقرأ الخطأ ليصحّح نفسه.
- **قلّل عدد الأدوات**: عشرون أداة متشابهة تربك النموذج أكثر مما تفيده. ادمج المتشابه.
- **افصل القراءة عن الكتابة**: أدوات القراءة تُنفَّذ بحرّية، وأدوات التغيير تمرّ بموافقة أو بحدّ صارم.

## بروتوكول MCP

مع تعدّد الأدوات والمصادر ظهرت حاجة إلى واجهة موحّدة بين النماذج والأنظمة الخارجية بدل تكامل مخصّص لكل مزوّد. هذا ما يقدّمه Model Context Protocol [2]: بروتوكول مفتوح يعرّف كيف يكتشف العميل الأدوات والموارد ويستدعيها. قيمته العملية أن أداتك تُكتب مرة وتُستهلك من أي عميل يدعم البروتوكول.

## الحواجز الإلزامية قبل الإنتاج

| الحاجز | القيمة العملية |
|---|---|
| حدّ أقصى للتكرار | ٥–١٠ دورات، ثم توقّف برسالة واضحة للمستخدم |
| سقف تكلفة للجلسة | إيقاف عند تجاوز عدد رموز محدّد |
| مهلة لكل أداة | تمنع تعليق الحلقة على استدعاء بطيء |
| صلاحيات أقل ما يمكن | مفتاح للقراءة فقط ما لم يلزم غير ذلك |
| موافقة بشرية | إلزامية لكل فعل غير قابل للتراجع (دفع، حذف، إرسال) |
| سجلّ كامل | كل استدعاء ومدخلاته ونتيجته — بلا هذا لا يمكن تصحيح فشل |

الحاجز الأهم أمني: نتيجة الأداة **بيانات لا تعليمات**. إن كان الوكيل يقرأ صفحة ويب أو بريدًا، فقد تحتوي تعليمة مزروعة تحاول توجيهه [3]. عالِج مخرجات الأدوات كمحتوى غير موثوق دائمًا، ولا تسمح لها بتوسيع صلاحيات الوكيل.

## متى لا تحتاج وكيلًا

هذا أهمّ قسم في المقال. الوكيل يُدخل عدم حتمية في نظامك: المسار يختلف بين تشغيلين، والتكلفة متغيّرة، والتصحيح أصعب. إن كانت الخطوات معروفة مسبقًا، فالخطّ الثابت أفضل في كل شيء:

| النمط | المسار | متى يُختار |
|---|---|---|
| خطّ ثابت | سؤال ← استرجاع ← توليد إجابة | الخطوات معروفة مسبقًا: أرخص وأسرع وقابل للاختبار |
| وكيل | سؤال ← قرار (بحث؟ حساب؟ استعلام؟) ← تنفيذ ← إعادة تقدير | المسارات لا تُعدّ مسبقًا وتختلف باختلاف السؤال |

القاعدة: ابدأ بالخطّ الثابت. انتقل إلى الوكيل حين تعجز عن تعداد المسارات مسبقًا — لا قبلها.

## الأخطاء الشائعة

1. حلقة بلا حدّ تكرار — أول سبب لفواتير مفاجئة.
2. أدوات كثيرة متداخلة الوظائف.
3. أخطاء أدوات صامتة أو غامضة، فيعيد الوكيل المحاولة نفسها بلا نهاية.
4. منح الوكيل صلاحيات كتابة واسعة «للتجربة».
5. معالجة مخرجات الأدوات كأنها تعليمات موثوقة.
6. غياب التقييم: الوكيل لا يُقاس بالانطباع بل بمعدّل إنجاز المهمة وعدد الخطوات وتكلفتها.

## الأسئلة الشائعة

### ما الفرق بين استدعاء الأدوات والوكيل؟
استدعاء الأدوات قدرة: النموذج يطلب تنفيذ دالة ويستقبل نتيجتها. الوكيل نمط يستخدم هذه القدرة داخل حلقة تكرارية مع قرار مستقل في كل دورة. كل وكيل يستدعي أدوات، وليس كل استدعاء أداة وكيلًا.

### كم عدد الأدوات المناسب؟
ابدأ بأقل عدد يغطّي المهمة — غالبًا ثلاث إلى سبع. عند التوسّع، جمّع الأدوات في مجموعات وقدّم للوكيل ما يخصّ سياقه الحالي فقط بدل عرض القائمة كاملة.

### هل تعدّد الوكلاء أفضل من وكيل واحد؟
ليس افتراضيًّا. تعدّد الوكلاء يضاعف التكلفة ونقاط الفشل، ويُبرَّر حين تكون المهام منفصلة فعلًا وتحتاج أدوات وصلاحيات مختلفة. جرّب وكيلًا واحدًا بأدوات جيدة الوصف أولًا.

### كيف أقيس أداء وكيل؟
بأربعة أرقام: معدّل إنجاز المهمة على مجموعة سيناريوهات ثابتة، متوسط عدد الخطوات، التكلفة لكل مهمة، ومعدّل الأفعال الخاطئة غير القابلة للتراجع. الأخير هو المقياس الأمني الحاسم.
